## Context Map

### Baseline Architecture at Design Approval

At design approval, Atelier was a source-only Claude Code plugin. Claude Code discovered skills from
`skills/`, agents from `agents/`, and public commands from `bin/`. Codex support is an imperative
mirror implemented by `bin/sync-codex`. OpenCode has no repository-owned integration.

There was no Cargo package at design approval. Executable behavior was spread across POSIX shell, Bash,
Nushell, Python, and jq, with several duplicate implementations that have drifted apart.

### Files to Replace or Generate

| ------------------------------------------ | ---------------------------- | ------------------------------------------------ |

### Existing Callers

The handoff, handon, handdown, handover, handup, eod, project-pulse, and triage skills
invoke the legacy commands or describe their contracts. The `justfile` invokes `sync-codex` from
all installation paths. Repository Git configuration points `core.hooksPath` at `.githooks`.

### Baseline Test Coverage at Design Approval

At design approval, no active automated tests covered public commands, installation, harness parity, or Git hooks. The
only diagram test is excluded from normal automation, imports the wrong implementation path, and
expects obsolete output.

### Reference Patterns

- `.claude-plugin/plugin.json` defines the current Claude-native plugin surface.
- `bin/sync-codex` defines current Codex installation locations and command aliases.
- `skills/*/agents/openai.yaml` defines existing Codex interface metadata.
- `agents/*.md` and `skills/*/SKILL.md` remain canonical prompt content.

### Risk Flags

- Migrating interpreter-invoked files breaks calls such as `sh helper.sh`, `nu helper.nu`,
  `uv run helper.py`, and `jq -f infer-json-schema.jq`.
- A compiled runtime requires platform-specific distribution for macOS, Linux, and Windows.
- Existing duplicate implementations disagree on timestamps, output streams, diagrams, and exit
  codes, so compatibility must be selected explicitly and tested independently.
- Existing SQL uses string interpolation and must not preserve injection behavior.
- The legacy pre-push hook creates commits while pushing. That behavior may exist only in its
  explicit compatibility profile, never in the canonical profile.
- OpenCode lifecycle hooks require a JavaScript or TypeScript plugin module.

## Goal

Provide one Rust-owned capability model, generator, installer, hook runtime, and legacy command
runtime that supports Claude Code, Codex, and OpenCode without duplicating workflow behavior.

## Approved Approach

Use the approved **Canonical Capability Model**: one harness-neutral manifest feeds sealed native
adapters, while generated artifacts contain no workflow logic except the unavoidable OpenCode
transport shim.

## Constraints

- Rust owns all first-party executable behavior.
- All maintained legacy scripts migrate into the Rust runtime.
- Claude Code, Codex, and OpenCode are the first reference adapters.
- macOS, Linux, and Windows are first-release targets.
- Existing implementation variants remain available through compatibility profiles.
- Alias inference and explicit `--compat` selection both remain supported.
- The OpenCode JavaScript shim may transport events but may not contain policy or workflow logic.
- Generated output must never delete or overwrite unmanaged user files.

## Crate Ownership

- **Owner package**: `atelier-cli` at the repository root.
- **Library crate**: `atelier`.
- **Binary**: `atelier`.
- **Rust edition**: 2024.
- **Minimum Rust version**: 1.88, required by `time = 0.3.55`.
- **Publishing**: `publish = false`; the library exists for separation and testing, not as a
  crates.io API.
- **Single responsibility**: translate Atelier's canonical capabilities into harness-native
  installations and execute the behavior those installations invoke.
- **Affected crates**: none; this is the repository's first Rust crate.

The binary is a multicall executable. Installed aliases preserve public command names and select
legacy profiles from the full invocation path. The root package is preferable to a workspace
because no other crate exists and the approved scope has one runtime owner.

## Public API

All fields shown below are private to their defining module. Crate-private constructors and access
methods compose them internally without expanding the supported API. Public functions and traits
exist for the binary/library split and integration tests; the package is not published and makes no
external semver commitment. Every exposed type derives `Debug`; value types additionally derive
the applicable `Clone`, `PartialEq`, `Eq`, and `Hash` traits.

Receipts are JSON files at `<state-root>/receipts/<harness>-<scope>.json`. A path or structured
document key may be replaced or removed only when the previous receipt names it and its stored hash
matches current content. User-modified or unmanaged targets produce a conflict.

SHA-256 inputs use an explicit framed representation:

- File: `file\0<executable:0|1>\0<exact bytes>`.
- Executable copy: `exe\0<exact bytes>`.
- Link: `link\0<normalized target path as UTF-8>`.
- JSON/TOML key: `document\0<format>\0<key path joined by NUL>\0<canonical value>`.

Canonical document values recursively sort object keys, preserve array order, and serialize without
insignificant whitespace. TOML values first convert into the equivalent JSON scalar, array, or
object representation. Hash checking extracts only the owned key, so unrelated user edits in the
same document do not conflict.

Application is failure-atomic rather than globally atomic: all content is first written beneath
the target's parent as `.atelier-stage-<transaction-id>`, each replaced target is backed up beside
it as `.atelier-backup-<transaction-id>`, and a JSON journal at
`<state-root>/journals/<transaction-id>.json` records every completed operation. Transaction IDs
are `<harness>-<process-id>-<unix-nanoseconds>`. Failure rolls operations back in reverse order; the
receipt is replaced last. Every mutating command runs `recover_generation` before creating a new
transaction and rolls back any journal without a committed receipt. This guarantees recovery from
an interrupted multi-root installation while acknowledging that unrelated filesystem locations
cannot be swapped in one OS operation.

The receipt is the commit point. Before replacement, the journal stores the exact previous receipt
bytes and the expected SHA-256 of the next receipt. Recovery compares the live receipt hash with
`next_receipt_sha256`: a match commits the transaction and removes backups even if the journal still
says `Applying`; a mismatch rolls back completed operations and atomically restores the previous
receipt bytes. `Committed` journals are cleanup-only.

`core.hooksPath` is a `ManagedTarget::GitConfig`. Planning reads its current value into
`GenerationContext::external_state`. Installation refuses a non-receipted value unless adoption is
selected, records both previous and managed values, and changes it through `ProcessRunner`.
Uninstallation restores the previous value only when the live value still equals the receipted
managed value; otherwise it reports an ownership conflict.

`atelier.toml` declares `core.hooksPath = ".githooks"` in `legacy_git_config`.
`ReplaceKnownLegacy` treats that exact pair as adoptable legacy state, records `.githooks` as the
previous value, and then installs the managed hooks-directory value. No other existing Git config
value is replaced automatically.

Resolution order is explicit `--compat`, full invocation path, executable basename, then
`Canonical`. Compatibility preserves documented arguments, output destinations, exit status, and
variant-specific formatting. It does not preserve injection, unsafe path handling, or dependence

## Data Flow

1. **Manifest source**: `atelier.toml` identifies canonical skills, agents, binaries, lifecycle
   actions, requirements, and portability.
2. **Snapshot loading**: `load_generation_context` walks every declared source beneath
   `source_root`, reads exact bytes through `FileSystem`, resolves `git rev-parse HEAD` through
   `ProcessRunner` when `VersionSource::GitHead` is selected, and loads the prior receipt from
   `state_root`.
3. **Validation**: the capability module validates identifiers and snapshot paths, then each sealed
   adapter reports native, adapted, or unsupported capabilities.
4. **Generation**: an adapter combines the manifest with `GenerationContext`, including the prior
   receipt, into a deterministic `GenerationPlan` without touching the filesystem.
5. **Installation**: the filesystem port stages the plan, verifies ownership and SHA-256 hashes,
   journals replacements, rolls back on failure, and replaces the receipt last.
6. **Hook ingress**: Claude and Codex command hooks invoke `atelier hook` directly; OpenCode's
   generated JavaScript shim serializes its native event and invokes the same command.
7. **Hook execution**: the selected adapter decodes native input into `HookRequest`; the manifest
   resolves an `ActionDefinition`; `RustHookHandler` returns `HookResponse`; the adapter encodes the
   harness-native decision.
8. **Legacy ingress**: argv-0 and `--compat` select a profile before dispatching into shared Rust
   handoff, schema, package, or Git-hook operations.
9. **Legacy egress**: the profile renders historical output formatting and exit status while core
   storage and path handling remain safe.

## Hexagonal Boundaries

- **Ports**: `FileSystem`, `ProcessRunner`, `Clock`, `Environment`, and `HandoffStore` in
  `atelier::host`.
- **Production adapters**: `OsFileSystem`, `OsProcessRunner`, `SystemClock`, and
  `SqliteHandoffStore` in `atelier::host`.
- **Harness port**: sealed `HarnessAdapter` in `atelier::harness`.
- **Harness adapters**: `ClaudeAdapter`, `CodexAdapter`, and `OpenCodeAdapter`.
- **Domain logic**: capability validation, generation planning, compatibility selection, hook
  decisions, handoff transformations, rendering, and schema inference perform no direct I/O.

No dependency cycle is introduced: `cli` depends on domain modules and ports; production adapters
depend on ports and external libraries; domain modules do not depend on `cli` or production
adapters.

### CLI and Installation Roots

The canonical CLI surface is:

```text
atelier validate [--manifest PATH]
atelier generate --harness HARNESS [--source-root PATH] --target-root PATH [--dry-run]
atelier install --harness HARNESS [--scope user|project] [--target-root PATH]
                [--dry-run|--adopt|--replace-known-legacy]
atelier hook --harness HARNESS --event EVENT --action ACTION
atelier handoff init|detect|migrate|db|reconcile|render|diagrams
atelier schema infer
atelier repo-hook pre-commit|pre-push|post-commit
```

Default roots are resolved without a directory-discovery dependency:

- Executables: `$ATELIER_BIN_DIR`; otherwise `$HOME/.local/bin` on macOS/Linux and
  `%LOCALAPPDATA%\Atelier\bin` on Windows.
- State: `$ATELIER_STATE_DIR`; otherwise `$XDG_STATE_HOME/atelier`,
  `$HOME/.local/state/atelier`, or `%LOCALAPPDATA%\Atelier\state` on Windows.
- Claude project generation: repository root. User installation delegates plugin activation to
  the `claude` command after installing the Rust executable.
- Codex user installation: `$CODEX_HOME`, otherwise `$HOME/.codex`.
- OpenCode user installation: `$OPENCODE_CONFIG_DIR`, otherwise `$XDG_CONFIG_HOME/opencode`,
  otherwise `$HOME/.config/opencode`.
- Project installation: the selected repository's `.claude`, `.codex`, or `.opencode` directory.

`--target-root` always overrides defaults and is mandatory for `generate`; tests never write to a
real home directory.

First installation is strict by default. `--adopt` records an existing path, link, executable, or
document key only when its canonical hash exactly matches the planned artifact. The one-time
`--replace-known-legacy` mode may replace only paths listed in the manifest legacy artifact
inventory whose current hash matches a golden legacy artifact hash shipped in `atelier.toml`; every
mismatch remains a conflict. The legacy artifact inventory also includes the current
`.claude-plugin/plugin.json`, all 13 `agents/openai.yaml` files, current Codex links, and `.githooks`
files. These modes are mutually exclusive, are shown in dry-run output, and never adopt an entire
user-owned configuration file.

Each `LegacyArtifact.path` is relative to its `LegacyRoot`, not necessarily the repository. Current
Codex links use `LegacyMatcher::SourceLink`; `.claude-plugin/plugin.json` uses
`JsonIgnoringKeys` with only `version` ignored; all other fixed files use `Sha256`. Ignored JSON keys
are removed before canonical hashing, so Git-stamped versions do not invalidate known-legacy
matching.

Replace `sync-codex` with adapter generation and installation. Generate skill interface metadata,

### OpenCode

Generate `.opencode/skills`, `.opencode/agents`, configuration fragments, and one JavaScript plugin
shim. The shim may map OpenCode callback arguments into JSON, invoke `atelier hook`, and apply the
returned native response. It may not inspect policy, choose outcomes, implement fallback behavior,
or duplicate Rust domain logic.

The shim resolves the executable from `$ATELIER_BIN`, falling back to `atelier` on `PATH`. It
registers only lifecycle callbacks declared by the manifest, writes one JSON object to child stdin,
reads one JSON object from child stdout, treats a nonzero child status as a plugin error, and applies
the already encoded response. Adapter fixtures exercise this contract even when the repository
manifest declares no plugin-owned lifecycle binding.

### Hook Wire Contract

Claude and Codex command hooks pass their native JSON object unchanged to stdin. Their codecs
extract `session_id`, `cwd`, and `hook_event_name`; all remaining fields stay in
`HookRequest::payload`. The OpenCode shim sends exactly:

```json
{
  "session_id": null,
  "cwd": "/workspace",
  "hook_event_name": "tool.execute.before",
  "input": {},
  "output": {}
}
```

The OpenCode `input` and `output` values are the unmodified callback arguments. The Rust response
uses the native encoding selected by the adapter:

```json
{
  "decision": { "kind": "continue" },
  "additionalContext": null,
  "diagnostics": []
}
```

OpenCode decision objects are exactly `{"kind":"continue"}`,
`{"kind":"block","reason":"..."}`, or
`{"kind":"replace-input","input":<JSON value>}`. `additionalContext` must be null for the two
supported OpenCode callbacks. Diagnostics are strings written by the shim to stderr after the
decision is applied. Unknown keys, unknown decision kinds, malformed JSON, or trailing non-whitespace
bytes are plugin errors; the shim never falls back to an allow decision.

| `HookDecision` | Claude/Codex                                        | OpenCode shim                                             |
| -------------- | --------------------------------------------------- | --------------------------------------------------------- |
| `Continue`     | Exit 0 with no stdout                               | Return without mutation                                   |
| `Allow`        | Native permission allow where the event supports it | Unsupported unless the callback has an allow concept      |
| `Block`        | Native deny/block JSON for the event                | Throw the Rust-provided reason                            |
| `ReplaceInput` | Native `updatedInput` for pre-tool events           | Replace `output.args` with the Rust-provided value        |
| `AddContext`   | Native `additionalContext` where supported          | Unsupported unless the callback exposes context injection |

The first-release event/decision matrix is:

| Harness event                                                                                                         | Allowed decisions                                                         |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Claude/Codex `SessionStart`, `UserPromptSubmit`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`, `Stop` | `Continue`, `Block`, `AddContext` where the native event supports context |
| Claude/Codex `SessionEnd`                                                                                             | `Continue` only                                                           |
| Claude/Codex `PreToolUse`                                                                                             | `Continue`, `Allow`, `Block`, `ReplaceInput`, `AddContext`                |
| Claude/Codex `PermissionRequest`                                                                                      | `Continue`, `Allow`, `Block`                                              |
| Claude/Codex `PostToolUse`                                                                                            | `Continue`, `Block`, `AddContext`                                         |
| Claude `PostToolUseFailure`                                                                                           | `Continue`, `Block`, `AddContext`                                         |
| OpenCode `tool.execute.before`                                                                                        | `Continue`, `Block`, `ReplaceInput`                                       |
| OpenCode `tool.execute.after`                                                                                         | `Continue`, `Block`                                                       |

Claude-only lifecycle events outside this table and OpenCode's generic observational `event`
callback are representable as harness-specific capabilities but are `Unsupported` in the first
release unless their action declares only `Continue`.

Validation rejects a lifecycle binding when its action can return a decision unsupported by that
harness and event. Codecs are event-aware; they do not assume one output schema works for every
lifecycle event.

Harness-native matchers decide whether a generated hook runs. Every generated hook command embeds
the binding's stable `--event` and `--action` values. At runtime `resolve_hook_action` requires one
manifest binding with the same harness, event, and action; absence or ambiguity is an error. The
runtime does not reimplement harness matcher syntax or choose among multiple matching hooks. If a
harness launches several matching hooks, each declared action runs independently under that
harness's native ordering and precedence rules.

### Legacy Commands

Install the `atelier` executable plus aliases for public command names. For legacy helper paths,
the installer uses links on Unix and executable copies where links are unavailable. In-repository
callers use canonical commands with explicit compatibility profiles.

Interpreter-specific invocation syntax is not preserved. A generated compatibility report names
every affected path and replacement command.

### Repository Git Hooks

The installer creates a managed hooks directory containing Rust executable aliases and configures
`core.hooksPath` to that directory. Unix uses links when safe; Windows uses executable copies and
must pass native Git hook conformance tests. The canonical pre-push hook does not create commits.
The old mutation remains available only under `CompatibilityProfile::GitPrePush`.

On Windows, user command aliases are full PE copies named `<alias>.exe`; compatibility resolution
strips one case-insensitive `.exe` suffix before basename lookup. Git hook copies retain the exact
extensionless names `pre-commit`, `pre-push`, and `post-commit` while containing the same PE bytes as
`atelier.exe`; Git for Windows invokes those paths directly. `set_executable` is a documented no-op
on Windows. Script deletion is blocked unless a native Windows conformance test proves all three
extensionless PE hooks execute and receive Git's argv/stdin contract.

### Bootstrap and Distribution

Harness marketplaces do not bootstrap the native runtime. The first release supports two explicit
bootstrap paths:

1. From a checkout on every platform: `cargo install --path . --locked`, followed by
   `atelier install --harness claude`, `atelier install --harness codex`, or
   `atelier install --harness opencode`.
2. From a release archive: download the archive matching the native target, place `atelier` or
   `atelier.exe` in the documented executable root, then run the same install command.

Claude marketplace installation remains available for prompt content, but any skill requiring the
runtime performs a PATH check and returns the exact remediation command instead of attempting a
script bootstrap. `just init` remains a developer convenience on systems with `just`; it is not the
cross-platform bootstrap contract. Release archives contain the native executable, `atelier.toml`,
`skills/`, `agents/`, and checksums. No Bash, PowerShell, Python, or Nushell installer is shipped.

## Verification

- White-box port and value tests live in `#[cfg(test)]` modules beside their defining modules, so
  private fields remain private. Black-box tests under `tests/` exercise `try_run`, `run_with`,
  `load_manifest`, and `load_generation_context` using fixture files and observable results rather
  than constructing private values directly.
- Unit tests cover manifest invariants, compatibility resolution, hook normalization, generation
  planning, handoff transformations, and schema inference using in-memory ports.
- Golden fixtures preserve every approved compatibility profile's stdout, stderr, files, and exit
  status for success and representative failure cases.
- Adapter fixtures cover skills, agents, hooks, binaries, permissions, requirements, and lifecycle
  mappings for Claude Code, Codex, and OpenCode.
- Generation tests prove deterministic output and idempotent repeated application.
- Ownership tests prove unmanaged and user-modified files are never removed or overwritten.
- SQLite tests use isolated bundled databases and parameterized queries.
- Installer tests cover interrupted staging, reverse-order rollback, journal recovery, and
  receipt-last replacement.
- Hook conformance tests replay native events for all three harnesses.
- CI executes formatting, clippy with warnings denied, tests, and release builds on macOS, Linux,
  and Windows.
- Release verification executes command aliases and native Git hooks on each target platform.

## Out of Scope

- Runtime orchestration or session transfer between harnesses.
- Emulating a capability a harness cannot represent safely.
- Harness adapters beyond Claude Code, Codex, and OpenCode.
- Publishing automatically to every harness marketplace.
- Migrating external tools such as git, doob, Claude, Codex, or OpenCode into the binary.
- Preserving interpreter-specific invocation syntax after script removal.

## Risk

- [x] **Breaking command changes**: interpreter-specific invocations are replaced by Rust commands;
      public direct command names remain aliases.
- [ ] **Breaking Rust API changes**: no existing Rust API exists.
- [x] **New external dependencies**: listed above and isolated behind ports where they perform I/O.
- [ ] **Feature flag required**: all first-release adapters are mandatory.
- [x] **Distribution change**: plugin installation now requires a matching Rust binary for macOS,
      Linux, or Windows.
- [x] **Generated code exception**: OpenCode requires a minimal JavaScript transport shim.
- [x] **Legacy ambiguity**: compatibility fixtures are mandatory because current variants disagree.
- [x] **Hook safety**: canonical pre-push behavior must not mutate Git history.

## Doublecheck

- Every type belongs to the single owner crate; no cross-crate or circular dependency exists.
- The public API exposes ports and stable domain values only; CLI parser details remain private.
- Filesystem, process, clock, and database I/O are behind explicit traits.
- Harness implementations are sealed to prevent unsupported third-party mappings.
- Generated-file ownership is represented explicitly and checked before mutation.
- The design introduces no async runtime, plugin marketplace abstraction, or fourth harness.
- Compatibility preserves observable contracts without preserving unsafe implementation defects.
